# go-e2e 使用场景

这些例子不是宣传口号，而是建议第一次使用时可以直接复制的任务。请根据项目实际情况调整路径和约束。

## 代码库理解

```text
分析这个仓库的目录结构、主要运行入口和测试入口。不要修改文件，最后给出：
1. 关键模块；2. 一条从命令到核心运行时的调用链；3. 我应该先阅读的五个文件。
```

适合：接手陌生项目、生成架构导览、准备技术评审。

## Bug 定位与修复

```text
复现并定位这个测试失败：<粘贴错误信息>。
先找出根因，再给出最小修复，补充回归测试，最后运行与改动相关的测试。
不要做无关重构。
```

适合：需要“分析 → 修改 → 测试 → 总结”的连续任务。

## 功能实现

```text
为 <模块> 增加 <功能>。
先阅读现有接口、数据结构和测试，列出实现计划；实现后补测试，运行聚焦测试，最后说明兼容性和未覆盖边界。
```

适合：把需求拆解成可以审查的实现闭环。

## 代码审查

```text
审查当前分支相对 main 的改动，重点检查：数据丢失、权限边界、并发、错误处理和测试缺口。
只报告有证据的问题，并引用文件路径、行号和复现方式。
```

适合：提交 PR 前做一次结构化检查。

## 测试与发布前检查

```text
检查本项目的构建、测试、格式化和文档生成链路。
先识别当前状态，再按优先级修复阻塞项；不要修改凭据、生成真实数据或删除用户文件。
最后给出可复现的验证命令。
```

适合：发布前验证和 CI 故障排查。

## MCP / Skills 扩展

```text
我想让 go-e2e 使用 <外部工具或工作流>。
请先说明应该使用 Provider、MCP、Skill、Tool 还是 Profile，给出最小实现路径和权限边界，
再列出需要修改的文件和验证方式。
```

适合：在扩展前先选对抽象，避免把业务逻辑硬编码进 Agent Loop。

## 任务写法建议

一个高成功率的任务通常包含：

1. **目标**：最终要得到什么结果；
2. **范围**：允许修改哪些目录；
3. **约束**：哪些文件、接口或行为不能改变；
4. **验证**：完成后必须运行什么测试或命令；
5. **交付**：最后需要输出哪些文件、证据和剩余风险。
