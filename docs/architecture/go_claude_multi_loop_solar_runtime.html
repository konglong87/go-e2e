Go Claude 多路闭环运行时架构

这张图把一条用户消息拆成五条并行控制路径：交付闭环、Level Gate、Query Loop、Trace 和 Checkpoint Loop。中心是同一个 query.Session，外圈是硬约束 gate、session transcript、trace 观测和可回滚锚点。

交付闭环：request → TaskContract → plan/do → ToolTrace evidence → gate → optional commit/readback → done
Level Gate：read/edit/Bash 触发硬闸门，证据不足时 block_continue 或 block_tool
Query Loop：LLM 返回 tool_use 就执行工具并回灌 tool_result，直到 final 通过
Trace：closure event 只进入可观测链路，不作为模型上下文恢复
Checkpoint：用户消息前建锚点，rewind/fork 恢复或分叉 session，metadata 不进模型上下文

ALL LOOPS

多路闭环控制面

用户消息进入后，runtime 不只等模型回答。它同时构建 TaskContract、记录 Action/Evidence/Delta、建立 checkpoint 锚点，并在工具前和 final 前执行硬 gate。

L0trivial_answer：无本地证据需求，允许直接回答，例如简单算术或语言解释。
L1no_tool_answer：不需要工具的说明类回答，final claim 仍不能伪称测试、搜索、提交。
L2read_only_scoped：用户要求读文件、总结、解释、比较时，Read/Grep/Glob/LS 或只读 Bash 是硬证据。
L3investigation_audit：排查、review、全局检查类任务，需要足够搜索/读取证据，避免“已全面检查”的空 claim。
L4local_change：Edit/Write 或写入型 Bash 后，需要 scope、metadata、semantic 三类 post-action delta 检查。
L5shared_state_change：commit/push/tag/deploy 等共享状态动作，工具前 gate 要求前置证据和授权。
硬约束Go 代码中的 gate 函数切片顺序执行，不是只靠提示词。
失败闭环工具失败也生成 tool_result，模型继续 loop 处理错误或修正路径。
Transcriptclosure/checkpoint metadata 在 resume sanitizer 里跳过，不污染模型上下文。
