历史扫描要求针对**实际拟公开 refs**，并且不能替代当前源码、安全、版权和发布验收。

这份清单用于把仓库从“可开发”推进到“可公开”。公开仓库是不可逆的外部状态变化：即使随后删除文件，fork、缓存、搜索索引和 Git 历史中仍可能保留副本。因此，发布结论必须基于扫描结果与人工复核，而不是仅凭当前工作区看起来干净。

## 使用方式

- 每次首次公开、迁移公开仓库或重大版本发布前，从干净的目标 commit 执行本清单。
- 为每个检查项保存命令、结果或审核链接；发现问题时先标记 `BLOCKED`，不要带风险发布。
- 需要重写历史、吊销凭据或移除第三方材料时，先备份并单独制定可回滚方案。

## 1. 许可证与知识产权

- [ ] 根目录存在 [LICENSE](../../LICENSE)，README 展示准确的许可证名称。
- [ ] 自有代码、文档、图片、字体、数据和生成物均有公开授权权利。
- [ ] 逐项核对第三方依赖、复制或改写的代码、协议字段、设计稿和截图来源。
- [ ] 需要保留的版权、许可证与 attribution 已进入源码、`LICENSE`、`NOTICE` 或第三方声明文件。
- [ ] 商标、产品名称和兼容性描述不会暗示未经授权的官方关系。

## 2. 当前文件脱敏

- [ ] 扫描 API Key、Token、密码、JWT、Cookie、私钥、连接串、Webhook 和云资源凭据。
- [ ] 搜索个人用户名、邮箱、绝对路径、设备名、内网 IP、私有域名、租户 ID 和真实用户数据。
- [ ] 检查 `.env*`、settings、日志、trace、transcript、数据库 dump、测试夹具和临时文件。
- [ ] 检查 Swagger/OpenAPI 示例与生成物，确保没有真实请求、响应或内部环境地址。
- [ ] 检查 Git 跟踪文件清单，确认构建产物、IDE 文件、缓存和本地工作目录没有被纳入。
- [ ] 更新 `.gitignore`，并用全新 clone 验证忽略规则。

建议至少组合使用两类密钥扫描器并人工复核命中项，例如 GitHub secret scanning、Gitleaks 或 TruffleHog。不要把扫描器“未命中”当成隐私审核已经完成。

## 3. 图片与文档审核

2026-09-10 本轮范围：前三项图片检查由维护者明确排除，不执行，也不记为审核通过。文档检查继续执行。以下图片条目保留供其他发布批次使用。

- [ ] 逐张打开 README、`docs/`、Issue 模板和 release 中的图片，而不只检查文件名。
- [ ] 对截图执行 OCR，检查路径、用户名、仓库名、会话内容、浏览器标签、通知和账号头像。
- [ ] 删除或重新制作包含内部项目、私有 session、真实任务、组织信息或敏感元数据的图片。
- [ ] 搜索文档中的内部域名、真实验收记录、个人目录和仅在本机存在的引用。
- [ ] 对公开保留的示例统一使用 `example.com`、占位凭据和合成数据。

## 4. Git 历史与身份信息

- [ ] 对**全部分支和 tag 的完整 Git 历史**执行密钥与隐私扫描，而不只扫描 `HEAD`。
- [ ] 复核已删除文件、历史配置、大文件、提交信息、author/committer 邮箱和签名信息。
- [ ] 明确接受公开的贡献者姓名与邮箱范围；个人邮箱需要时改用 GitHub noreply 地址。
- [ ] 若历史包含秘密，先吊销或轮换凭据，再重写历史；仅删除当前文件不能消除泄露。
- [ ] 若历史包含大量个人信息或无权公开材料，评估发布清理后的新仓库，而不是保留全部历史。
- [ ] 历史重写后重新扫描所有 refs，并通知已有 clone/fork 的协作者重新同步。

## 5. 构建、依赖与供应链

- [ ] 使用 CI 固定的 Go 和 Node.js 版本，从全新 clone 完成构建与测试。
- [ ] 执行 `go test ./... -count=1`、`go vet ./...`、格式检查和项目离线验收。
- [ ] 执行 `govulncheck ./...`，确认可达漏洞已修复或有公开、可接受的风险说明。
- [ ] 审核 `go.mod`、`go.sum`、npm lockfile 和 GitHub Actions，避免浮动或来源不明的关键依赖。
- [ ] 检查 workflow 权限、第三方 Action 固定方式、fork PR 行为及 secret 暴露边界。
- [ ] 生成 SBOM 或依赖清单，并确认 release 二进制可追溯到目标 commit。

## 6. 安装与发布产物

- [ ] 在干净环境验证 README 的 clone、配置、`doctor`、CLI 和 server 快速开始命令。
- [ ] 验证源码目录安装：`go install ./cmd/golang-cc`。
- [ ] 验证远程安装：`go install github.com/konglong87/go-e2e/cmd/golang-cc@<version>`。
- [ ] 确认 `go.mod` 不含会阻断远程模块构建的本地 `replace`，或在文档中明确阻塞状态。
- [ ] 在 Linux、macOS、Windows 的目标架构验证 release 二进制、校验和与版本信息。
- [ ] tag、GitHub Release、变更日志、二进制和容器镜像指向同一 commit。

## 7. 社区与安全治理

- [ ] [贡献指南](../../CONTRIBUTING.md)、[行为准则](../../CODE_OF_CONDUCT.md)和[安全策略](../../SECURITY.md)可访问且联系方式有效。
- [ ] GitHub Private vulnerability reporting 已启用并实际验证入口。
- [ ] CODEOWNERS、分支保护、必需检查、Issue/PR 模板和 Dependabot/Renovate 策略符合维护方式。
- [ ] README 清楚描述项目用途、安装、已知边界、许可证和安全报告入口。
- [ ] 明确维护者响应范围、支持版本以及实验性功能，避免对稳定性作超出证据的承诺。

## 8. 最终发布闸门

- [ ] 目标 commit 的 `git status` 干净，CI 必需检查全部通过。
- [ ] 从全新 clone 重跑链接、构建、测试、漏洞、密钥和历史扫描。
- [ ] 至少一位维护者复核扫描证据、许可证来源和 release 内容；截图按本轮明确的范围豁免记录处理。
- [ ] 已记录已知限制、风险接受人、回滚方案与发布后监控方式。
- [ ] 发布后立即检查公开仓库、README、安装命令、Release 下载和安全报告入口。

最终状态只能填写一个：

- `READY`：所有阻塞项完成，残余风险已有公开说明和明确接受人。
- `BLOCKED`：存在未处理的秘密、隐私、授权、可达高风险漏洞、安装失败或发布证据缺失。

> 当前仓库能通过测试或密钥扫描，并不自动等于可以公开。首次开源前必须单独完成知识产权、图片、Git 历史和个人信息审核。
